# Calendar & Forms security and operations

## Reviewed migration target

Existing **Syrka Workspace**, project `zguejzlseldovdssiumn`, Postgres 17, was inspected before applying the additive `20261101014831_native_calendar_forms`, `20261101045155_native_uploads_reminders`, `20261101050433_native_audit_counts`, `20261101051240_native_privilege_hardening`, `20261101051905_native_integrity_receipts` and `20261101053256_native_reminder_permissions` migrations. No existing `office_files`, `workspace_files`, Sessions tables/policies, Auth settings, production code, Campus/Roadmaps databases or production domains were replaced. Existing user rows are untouched. New names use `native_` and private `native_private`. The changelog's recent tzdata advisory was reviewed; no database upgrade was performed. Recurrence calculations use the application's Temporal timezone model.

## Access boundaries

Authenticated APIs verify the supplied Bearer JWT through `getUser(token)` and reject anonymous Auth users. RLS owns private calendars/forms/responses, and calendar shares authorize explicit viewer/editor roles. Viewers cannot read events marked private/busy or their exceptions. Account IDs are shared deliberately through the Account ID control; this release does not offer an email/account directory. Editors may modify shared events; only owners manage shares and reminders. Removing sharing revokes database access. No frontend service-role key is used.

Published schemas are insertable only by the signed server broker; clients have SELECT-only access to their own versions. A composite foreign key prevents attaching another form's version. Historical answers stay attached to their original version. The UI analyzes/exports one immutable version at a time. Form deletion is reversible soft deletion; response deletion is permanent and owner-only. Audit records contain action, actor/owner IDs, object ID and timestamp, never answers or provider prompts.

## Public responses

The public route is outside the Workspace editor shell and does not require Supabase anonymous sign-in. HTTPS public tokens are unguessable UUIDs and grant only the owner's configured respondent access. Owners' drafts, answer keys, responses and private account records never enter the public payload. Authenticated-only and one-per-user eligibility are enforced again inside the database. Anonymous/public submissions do not expose identities in owner-facing rows. Private eligibility maps are inaccessible to application roles.

Next validates question schemas, types, ranges, required visible answers, branching and attachment ownership. Rules refer only to earlier questions, preventing cycles; hidden sections/questions are not required or persisted. No custom JavaScript executes. React escapes rendered text. Dates are parsed with Temporal. Ratings/numeric ranges and consent are validated server-side. Public routes reject cross-origin writes, enforce a honeypot, payload limits and durable IP-HMAC rate windows (10/minute per operation). The Vercel-supplied forwarding header is trusted only on Vercel. Anonymous submissions cannot guarantee one-person-one-response; enable authenticated eligibility when needed. No CAPTCHA or identity verification is claimed. The application-level limiter is deliberately modest and may throttle users behind a shared NAT; adjust only after reviewing abuse constraints.

Database `SECURITY DEFINER` broker functions have an empty search_path, explicit relations and restricted EXECUTE grants. They accept only known operations with a server-only HMAC and timestamp within 90 seconds. Unsigned RPC calls fail. No generic SQL, arbitrary URLs or external keys are accepted. Server signing key `SYRKA_NATIVE_SIGNING_KEY` is a protected Vercel Secret, paired with `native_private.keys(id='v1')`; the private schema is not exposed and has no client grants. It is separate from Qwen, LiveKit and service-role credentials. Signed payloads and secrets are not returned to browsers or logged. A production release needs an explicitly reviewed key/deployment policy; do not copy the Preview secret into a NEXT_PUBLIC variable.

## Attachments

Private bucket `office-form-uploads` is separate from existing assets, max 2 MiB, PDF/PNG/JPEG/plain-text only. The server validates bytes/type/size and the visible question before registering an unguessable 256-bit storage path bound to response, form, version, question and receipt hash. Pending insert capability expires in one hour. Submissions require a real uploaded object with matching bindings. An upload cannot be attached to another response/form. Anonymous users cannot browse metadata or submitted objects. Owner downloads require Auth/RLS and a 60-second signed URL. Files are **not malware scanned**; the UI warns before download. No SVG/executable/HTML upload or inline rendering is offered.

Unsubmitted uploads older than one day and objects deleted through form metadata are collected through the signed daily worker and Storage API. Direct SQL deletion of `storage.objects` is not used. Cleanup reports failures without pretending files were removed. Expired orphan capabilities permit only exact unpredictable object paths, not bucket listing. A private garbage queue retains object paths when metadata is cascaded away.

## Durable reminders

Event masters store local wall times + IANA timezone + recurrence rules; exceptions reference the original local occurrence. Spring gaps are rejected for direct edits/skipped in recurrence, and autumn folds use an explicit earlier/later choice. Monthly dates such as the 31st skip missing month days. UTC timestamps are derived, not independent duplicated events.

The server seeds the next 90 days of reminder jobs after save. `pg_cron` job `syrka-native-reminder-delivery` runs each minute and atomically marks due jobs delivered plus inserts unique in-app notifications. Repeated delivery creates no duplicate inbox record. Daily `syrka-native-reminder-refill` uses `pg_net` and a short-lived HMAC header to invoke `/workspace/api/native/worker`, extending horizons and collecting orphan uploads. `native_private.worker_config` must point at the latest stable **Calendar/Forms Preview** alias; no secret is embedded in the cron command. The endpoint refuses unsigned/expired requests. No paid scheduler was provisioned. Email, background browser push and external calendar reminders are not configured and are not claimed.

Monitor `cron.job_run_details` for delivery status, `net._http_response` for refill HTTP results and worker aggregate counts. A paused database, blocked Preview or failed worker can delay future delivery; inspect failures before claiming reliability. Do not query or log private titles/answers merely for diagnostics. Rescheduling cancels pending jobs and creates jobs for the new time; delivered notifications remain historical. Notification delivery means insertion into the Syrka inbox, not an OS/email receipt.

## Qwen and costs

Roadmaps principles were inspected without reading/copying its secrets. Workspace's own general-purpose `SYRKA_AI_*` credentials and verified Singapore endpoint are reused. Only `qwen3.8-flash` is called, with explicit per-request consent, validated structured output, bounded requests, zero retries/fallback, existing Free Quota Only guards and entitlement expiry. Calendar sends only the user's authorized free/busy intervals and request; Forms drafting sends the request, never collected responses. No AI-published form, silent event write, paid fallback, Max/embedding/vision entitlement inheritance or automatic official grading is enabled. Provider failure preserves local editing. Provider-side Free Quota Only remains the hard billing guard.

## Advisor review

The hosted advisor found Supabase default function grants broader than local Postgres defaults. The fourth migration explicitly resets all new table/function privileges, then grants only the required operations; the RLS test now also simulates Supabase default grants. Anonymous callers cannot execute calendar membership helpers. Signed brokers remain intentionally callable by the server through the anon role and reject unsigned/expired requests. Private deny-all RLS tables deliberately have no application policies. The managed `pg_net` extension is non-relocatable and registered in `public` even though its networking objects live in `net`; the extension advisor warning is documented rather than dropping/recreating it. Client roles have no usage/execute privileges on `net`. Intentional security-definer advisor findings require this review, not blanket suppression. Existing leaked-password protection remains disabled; no paid feature or Auth setting was changed. [Supabase advisor guidance](https://supabase.com/docs/guides/database/database-linter).

Integrity follow-up: canonical event IDs/calendar IDs are checked in Postgres, and imported iCalendar UIDs are unique within a calendar. A purpose-bound receipt lookup returns only the original response ID/timestamp/confirmation to its secret receipt holder, so a retry after republishing/closing cannot create a duplicate or lose its receipt. Numeric/rating defaults, invalid dates and unsupported recurrence filters are validated explicitly. Week/day dragging converts the displayed timezone back into the event's timezone.

Shared-event reminder delivery rechecks the recipient's current calendar membership and event visibility at execution time. Revoking/changing sharing cancels pending jobs, and even a stale daily refill cannot disclose a newly private title to a revoked participant. Pending upload filenames are hidden from form owners until submission. Real signed worker testing caught and fixed a PL/pgSQL alias ambiguity in attachment garbage collection; the regression test now executes orphan enumeration, Storage-policy deletion and metadata cleanup rather than only testing upload registration.
